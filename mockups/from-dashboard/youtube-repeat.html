NOTES · OPEN QUESTIONS FOR MONKEY

Search backend: pick one

Pasting a link needs no backend at all. The page reads the video id from youtu.be/…, watch?v=…, /shorts/…, music.youtube.com and keeps &t=. Only typed search needs one of these:

(a) YouTube Data API v3 RECOMMENDED

  • Official and documented; a search.list call costs 100 of the 10,000 free daily units, so about 100 searches a day. One person looping songs shouldn't get near that.
  • Key kept server-side in (dashboard data folder)/yt-key.txt, the same pattern as site-token.txt. The browser only ever calls /api/ytsearch, which sits behind the site code like /api/gamesearch.
  • Stays stdlib-only: one urllib GET. No change to the container image.
  • Cost to you: create a Google Cloud project + API key (restricted to the YouTube Data API), then put it in that file.
  • Over quota → the page says so and paste-a-link still works.

(b) yt-dlp ytsearch on the NAS

  • No key, no quota.
  • Scrapes YouTube, which YouTube's terms forbid. A personal search box is low risk, but it's still a breach.
  • Breaks whenever YouTube changes its pages, and needs yt-dlp kept current. Today the container is plain python:3.11-slim, stdlib only, no build, so this means a pip install at start or a custom image. Watchtower won't keep it updated.
  • Slower: a few seconds per search vs. well under one.

Why (a): it doesn't change the container's "stdlib only, no build" design, it's the only clean option under the terms, and the quota is about 100× what this page should need. (b) is the fallback if you don't want a Google Cloud project.

Lifetime loop counter (added 2026-10-07)

  • Three numbers on screen: this session (the × 14 chip, resets on reload), this video's lifetime (gold), and all videos' lifetime. The recent list and search results show each video's lifetime count too.
  • Stored on the NAS in (dashboard data folder)/repeat-counts.json, one entry per video id: {"count", "title", "first", "last"}. The all-videos figure is the sum, so it can never drift from the per-video numbers. Same folder and atomic-write pattern as agenda.json.
  • One loop = one POST /api/repeat-count {"id"}, sent when the player reports the video ended. The server adds 1 under a lock and returns the new pair of counts. The browser never sends a number, so two open tabs can't overwrite each other. Behind the site code like every other /api/*.
  • If the NAS can't be reached, the page keeps pending loops in localStorage and sends them on the next success, so no loop is lost or counted twice.
  • Starts at 0 on launch. There's no history to backfill.

Counter questions for Monkey

  • A–B loops: does looping only a part count as a loop? My default: yes, one per pass back to A, in the same counter.
  • Skipping: does dragging back to the start count? My default: no. Only a natural end (or reaching B) counts.
  • Resetting: should there be a way to reset a video's count, or remove a video from the list? My default: no button. That would be a delete, and it can wait until you ask.

How it works (same for every layout)

  • A new route GET /repeat in status_collector.py serves a new repeat.html, behind the same site-code lock as /. Same container, no compose change. The dashboard's index.html only gains the chip.
  • Correction (2026-10-07): the × 14 chip drawn on the video in A/B/C breaks YouTube's embed rules ("you must not display overlays… in front of any part of a YouTube embedded player"). Removed from the video here; the session count already shows in the line under the player.
  • Looping uses YouTube's IFrame Player API: when it reports the video ended, it seeks to 0 (or to A for an A–B loop). That also counts the loops.
  • A–B points are stored per browser in localStorage. The recent list now comes from the NAS counter file (sorted by last played), so it follows you across devices for free.
  • Pasted-link titles come from YouTube's keyless oEmbed endpoint, so a pasted link shows its title even without option (a).

"Keeps playing while the tab is open": what I expect, untested

  • Desktop browsers keep a background tab's audio playing, and the loop is driven by the player's own events (not a timer), so it should keep looping. To verify on your PC once it's built.
  • Phones are the unknown: locking the screen or switching apps may pause embedded video. That's browser policy, not something this page controls. I'll test it on your phone before calling it done rather than promise it.
  • A screen wake-lock toggle ("keep screen on") is possible for phone use. Tell me if you want it.
